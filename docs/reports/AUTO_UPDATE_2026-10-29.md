# Автообновление игры — отчёт (29–30.10.2026)

Ветка `claude/auto-update`. Правила для команды — в [docs/RELEASES.md](../RELEASES.md).

## Как устроено

```
мерж PR в main
  └─ CI, задача Release (только push в main, по одной за раз)
       1. tools/next-version.mjs: последний тег vX.Y.Z на GitHub + метки смерженного PR → следующая версия
       2. npm run build + electron-builder --publish never -c.extraMetadata.version=X.Y.Z
       3. gh release create vX.Y.Z: Asterion-Setup-X.Y.Z.exe, .blockmap, latest.yml; заметки — ссылка на PR
установленная игра (electron/updater.cjs, electron-updater)
  ├─ при запуске (через 4 с) и по кнопке: «есть ли версия новее?» → GitHub Releases (latest.yml)
  ├─ скачивает в фоне, прогресс показывает в меню (preload: asterionDesktop.updates)
  └─ «Перезапустить и обновить» → сохранения синхронно записываются на диск → quitAndInstall → установщик → игра запускается снова
```

### Версии

- Формат semver `MAJOR.MINOR.PATCH`, без букв. electron-updater сравнивает версии по semver, буквы это сравнение ломают.
- По умолчанию растёт PATCH. Метка `release:minor` поднимает MINOR и обнуляет PATCH. Метка `release:major` поднимает MAJOR и обнуляет MINOR и PATCH.
- Источник истины — теги `vX.Y.Z` на GitHub (`git ls-remote`). В `package.json` всегда `1.0.0`. CI ничего не коммитит в `main`, поэтому нет ни петли CI, ни конфликтов.
- Метки берутся у PR, связанных с коммитами мержа `main` (first-parent) со времени последнего тега. Используется API `commits/{sha}/pulls`. Если GitHub отменил ожидающий запуск CI из-за быстрого второго мержа, следующий релиз всё равно учтёт оба PR. Из их меток берётся самая крупная, номер поднимается один раз.
- Если вычисленный тег уже есть, берётся следующий свободный PATCH.
- Первый релиз после мержа этого PR — **1.0.1** (тегов ещё нет, база 1.0.0).

### CI (`.github/workflows/ci.yml`)

- `package` (Windows installer) теперь запускается только на `pull_request` и `workflow_dispatch`. На PR, как и раньше, установщик лежит в artifact 14 дней.
- Новая задача `release`:
  - запускается только на `push` в `main`;
  - `permissions: contents: write` (и `pull-requests: read`) есть только у неё;
  - `concurrency: release-main`, `cancel-in-progress: false`;
  - `checkout` с `fetch-depth: 0`, чтобы считать коммиты от последнего тега;
  - ни от чего не зависит (`needs` нет). Если упадут NPC-проверки или long-horizon, релиз всё равно выйдет;
  - перед публикацией проверяет, что есть все три файла и что в `latest.yml` нужная версия. Если `gh release create` падает, задача падает с ошибкой.
- В логическую задачу добавлен шаг `npm run test:release`.
- Публикация идёт через `gh release create`, а не через `electron-builder --publish always`. Так тег, заметки и момент выпуска полностью в наших руках. `latest.yml` и `.blockmap` electron-builder всё равно создаёт по конфигурации `publish` (github, ratoker-jpg/Asterion).
- `package.json → build`: добавлены `nsis.artifactName = ${productName}-Setup-${version}.${ext}` (имя `Asterion-Setup-X.Y.Z.exe`) и `publish` (github, `releaseType: release`). `appId com.asterion.game` не менялся.

### Игра

- `electron/updater.cjs`. Работает только в упакованной игре (`app.isPackaged`). В dev, в QA-скриптах (они не грузят `main.cjs`) и при `ASTERION_DISABLE_UPDATES=1` в сеть не ходит. Настройки:
  - `autoDownload: true`;
  - `autoInstallOnAppQuit: false` — без кнопки ничего не ставится;
  - `allowPrerelease: false`, `allowDowngrade: false`;
  - `publisherName` и проверки подписи нет.
- Состояния (IPC `asterion:update:state`): `checking`, `available`, `downloading` (с %), `downloaded`, `error` (спокойный текст: «Нет связи с сервером обновлений» или «Не удалось проверить обновления»), `latest`.
- Меню: `src/ui/menu/GameUpdateRow.tsx` + `updates.css` (токены `--ut-*`, акценты расы `--race-*`).
  - Главное меню: блок под пунктами, в ширину колонки меню.
  - Меню паузы: строка под кнопками.
  - В браузерной сборке блок не показывается.
- **Сохранение перед перезапуском.** Кнопка сначала посылает событие `asterion:save-flush` (`SAVE_FLUSH_EVENT` в `src/application/save-storage.ts`):
  1. Хранилище больших сохранений переходит в синхронный режим и дописывает незаконченные асинхронные записи (как при закрытии окна).
  2. `App` записывает отложенное автосохранение и время игры. Это те же обработчики, что на `pagehide`/`beforeunload`.
  3. Только после этого main-процесс вызывает `quitAndInstall(true, true)`: тихая установка, затем перезапуск игры.
  - Если идёт прогон отсутствия, на диске остаётся последний шаг, который записал worker. После обновления прогон продолжается с него.
- Сохранения лежат в `%APPDATA%\asterion` (имя пакета `asterion`; `productName` в упакованный `package.json` не попадает). Папка установки — `%LOCALAPPDATA%\Programs\Asterion`. Установщик профиль не трогает (`deleteAppDataOnUninstall` выключен по умолчанию).

## Как выпустить major / minor

1. До мержа поставить на PR метку `release:minor` или `release:major`. Если метки ещё нет: `gh label create release:minor` / `gh label create release:major`, либо GitHub → Labels.
2. Смержить. Через несколько минут на странице Releases появится `vX.(Y+1).0` или `v(X+1).0.0`.

Обычный PR без метки даёт `X.Y.(Z+1)`.

### Настоящее обновление (локальный сервер, generic provider)

Тестовые сборки сделаны с отдельной конфигурацией (только в scratchpad, не в репозитории):

- `productName/appId = AsterionUpdateTest / com.asterion.game.updatetest`, чтобы не трогать настоящий профиль `%APPDATA%\asterion` с сохранениями владельца;
- `publish = generic http://127.0.0.1:8765/`.

В продакшене остаётся github. Версии 1.0.1–1.0.4 раздавались `python -m http.server`.

**Прогон 1: 1.0.1 → 1.0.2, большое файловое сохранение и прогон отсутствия**

1. Установил 1.0.1 (`/S`). Сервер ещё не запущен: в меню «Версия 1.0.1 · Нет связи с сервером обновлений · попробуйте позже», без окон с ошибкой (скриншот 01).
2. Запустил сервер с 1.0.2. Игра сама нашла и скачала обновление (~640 МБ). В меню «Версия 1.0.2 готова к установке» и кнопка «Перезапустить и обновить».
3. Записал в профиль большой мир дня 2 (39,9 млн символов) как файловое сохранение. Открыл кампанию на час позже её времени: начался прогон отсутствия. Worker записал прогресс на диск.
4. Посреди прогона открыл меню паузы и нажал «Перезапустить и обновить» (скриншот 03). При нажатии сохранения записались на диск (файлы 00:02:39 и 00:02:40). Установщик поставил 1.0.2.
5. Запустил 1.0.2:
   - «Версия 1.0.2 · Установлена последняя версия»;
   - «Продолжить» показывает слот;
   - на диске прогресс прогона, записанный до нажатия (`processedThroughAt` 1767398931821 > исходного 1767398400000);
   - кампания открылась без ошибки сохранения, прогон продолжился (скриншот 05).

В этом прогоне игра после установки сама не перезапустилась. Причина — окружение проверки: игра была запущена из песочницы агента, и установщик не смог запустить её от имени пользователя (`ExecShellAsUser`). Прогон 2 сделан без песочницы.

**Прогон 2: 1.0.2 → 1.0.3 → 1.0.4, обычный запуск через ярлык, настоящий профиль**

1. 1.0.2 запущена через проводник, как её запускает игрок. Обновление до 1.0.3 скачалось. После «Перезапустить и обновить» установщик отработал, и **игра сама запустилась снова** примерно через 2 с (скриншот 02 — состояние до нажатия).
2. В профиль этой установки записано то же большое сохранение (39 880 857 символов, sha256 `4c6a65cf…a18ccb`). Нажата «Проверить обновления»: нашлась 1.0.4, скачалась. Нажата «Перезапустить и обновить»: установка заняла 18 с, игра перезапустилась сама, в реестре версия 1.0.4.
3. После обновления (скриншот 04): «Версия 1.0.4 · Установлена последняя версия», «Продолжить: Прежнее сохранение · Астеры». Указатель и файл сохранения на месте, **sha256 совпадает байт в байт**.

После проверки тестовая установка, её профиль и кэш обновлений удалены.

## Ограничения и что осталось владельцу

- **Подписи нет.** При первой установке SmartScreen может предупредить («Подробнее» → «Выполнить в любом случае»). Обновления ставятся тихо.
- Установщик весит около 640 МБ. Дифференциальная загрузка по `.blockmap` включена: electron-updater скачивает только изменённые блоки, если есть blockmap прошлой версии.
- Метки `release:minor` и `release:major` в репозитории нужно создать один раз. Я их не создавал: это изменение репозитория, его делает владелец.
- Первый настоящий релиз (`v1.0.1`) появится только после мержа, его проверит первый запуск задачи Release на `main`.
- Уже установленные старые сборки (собранные до этого PR) обновляться не умеют. Их нужно один раз переустановить из релиза `v1.0.1`.

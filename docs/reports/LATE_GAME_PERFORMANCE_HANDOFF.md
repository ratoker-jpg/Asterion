## Что сделано

### Детерминизм прогона (красные CI-задачи main)
Прогон теперь даёт один и тот же мир при любой нарезке на куски, через воркер и после
сохранения/загрузки посреди прогона:
- `attack.ts`: командир, погибший до последнего, удаляется из снимка планеты (как при загрузке);
- `reconcile.ts`: владельцы целей повторного шпионского отчёта NPC досчитываются на момент решения;
- журнал разведки ограничивается так же, как при загрузке (256 контактов и т. п.);
- рекорды очков в журнале разведки — в порядке id (байты не зависят от нарезки);
- квитанции улучшений космодрома NPC — общее окно 64;
- блокировка перенаселения снимается в точный момент сжигания, этот момент — контрольная точка прогона;
- итог мира: пока игрок читает законченную сводку, короткий хвост прогона её не заменяет
  (падение full-world Electron QA «world summary invalid»).

Проверено: `ASTERION_NPC_LONG_HORIZON=1 npm run test:npc` — 176/176 (включая 30-дневные
проверки, падавшие на main); новый тест `npc-catchup-slicing.test.ts`.
Поведение NPC/правила не менялись; итоговые миры отличаются от main ровно этими исправлениями.

### Ускорение прогона (поведение не меняется — дайджесты сверены)
Каждый коммит оптимизации сверен по дайджесту: полный мир 6 ч (`8ce7cafe…`) и мир дня 1 + 30 мин
против эталона после исправлений детерминизма (коммит 4f6e30b, `cb6df959…`).
- Прогон вынесен в Web Worker (`src/npc-catchup.worker.ts`, `npc-catchup-runner.ts`): куски ~250 мс,
  прогресс в окно через маленький стор, сохранение прогресса раз в 15 с сериализуется в воркере,
  в конце берутся только изменённые поля сохранения; без воркера — прежний путь.
- На контрольной точке полёта досчитываются только владельцы, которых касаются её полёты
  (раньше — все владельцы с живыми полётами).
- Кэши/индексы: следующий момент планеты, владельцы→планеты, очки владельца (по читаемым полям),
  системы для решений NPC (по видимым временным объектам), карта для кандидатов миссий,
  отпечаток систем для рейдов, архив полётов, помощь, пиратский контакт, выбор следующего полёта.
- Расписание временных объектов хранится в типизированных массивах (~1 ГБ кучи → ~0,1 ГБ вне кучи).

### FPS
- Автосейв тиков часов стоит ≤ ~2% главного потока (маленькие сохранения — каждый тик, большие — реже,
  сброс при закрытии окна).
- Экран боевых докладов не перечитывает сохранение из localStorage каждую секунду.
- Расписания временных объектов строятся в простое (`requestIdleCallback`), а не в кадре.
- Свежий полный мир, GPU 120 Гц: все 6 экранов 120 FPS, p95 8,4 мс, 0 длинных задач
  (до: длинные задачи ~200 мс каждые 1–2 с, `ensureTimedCycles` в кадре).

Цель «24 ч на мире дня 7 за 1–2 минуты» **не достигнута**: в поздней игре ~50% времени —
решения NPC (`applyNpcAutonomyAttention`: кандидаты миссий ~18%, контекст полезности ~7%,
помощь, пираты), ~13% — `reconcileFlights` (проход по тысячам живых полётов на каждое событие),
~12% — `pruneCampaignHistory`. Оставшееся размазано; нужен следующий шаг — инкрементальные
индексы полётов по времени события и удешевление одного «взгляда» NPC (кандидаты по семействам).

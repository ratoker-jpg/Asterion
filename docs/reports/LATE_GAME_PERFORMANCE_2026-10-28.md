# Производительность поздней игры — отчёт (28–29.10.2026)

PR: ratoker-jpg/Asterion#116 (ветка `claude/late-game-performance`). Сырые цифры — `LATE_GAME_PERFORMANCE_2026-10-28.json` рядом.

## Коротко

- **Прогон отсутствия больше не замораживает игру.** Он идёт в Web Worker; во время прогона
  интерфейс держит ~60 FPS (на main — 0,6–1,8 FPS, кадры по 0,7–5 с).
- **Прогон в 3–5 раз быстрее в игре, и разрыв растёт к поздней игре:**
  1 ч отсутствия на мире дня 1 — 123 → 37,6 с; дня 2 — 523 → 104 с; дня 3 — 150 с (на main мир дня 3
  даже не сохраняется); в Node на дне 3 — 44 мин → 2,7 мин (×16).
- **FPS в простое.** День 1: на main 35–40 FPS, p95 кадра 83–100 мс; на ветке 59–60 FPS, p95 16,8 мс.
  День 2: на main 0,4–4 FPS (задачи по 1–5 с); на ветке 56–59 FPS. День 3: 54–58 FPS. Фризов автосейва
  нет; на днях 2–3 остаются 2–7 задач по 100–300 мс за 8 с — живая симуляция 100 NPC.
- **Прогон детерминирован:** один мир при любой нарезке, через воркер и после сохранения/загрузки
  посередине. Красные long-horizon проверки main проходят (176/176).
- **Цель «24 ч на мире дня 7 за 1–2 минуты» не достигнута.** 1 ч прогона в Node: день 1 — 42,5 с, день 2 — 110 с, день 3 — 162 с; по тренду (+55–60 с на игровой
  день) день 7 — ~380 с на игровой час, то есть сутки ~2,5 ч (оценка, день 7 не сгенерирован). Что дальше — план «максимум»
  в конце.
- **Две серьёзные проблемы сохранений найдены и исправлены:**
  1. пиратский профиль из другого JS-движка делал сохранение «повреждённым»;
  2. к третьему дню мир (58 млн символов) переставал помещаться в localStorage (предел Electron 44 —
     ~52,3 млн). Теперь большое сохранение лежит файлом в профиле игры, в localStorage — указатель;
     старые сохранения переезжают сами при первой записи.
- **Живая игра на дне 3** после доводки: секунда игры стоит UI-потоку ~76 мс (медиана; было ~190–220),
  автосейв больше не даёт фризов по 0,5–0,7 с — он считается кусками между кадрами и пишется на диск
  главным процессом. Пики одной группы решений NPC (40–110 мс) остались — см. план «максимум».

## Сохранение

| Мир | Символов | `JSON.stringify` целиком | новая сериализация: первая / после тика | самый длинный шаг автосейва |
|---|---|---|---|---|
| День 0 | 0,27 млн | 2 мс | — | — |
| День 1 | 18,9 млн | 101 мс | 129 / 46 мс | 16 мс |
| День 2 | 39,9 млн | 206 мс | 254 / 111 мс | 32 мс |
| День 3 | 57,7 млн | 287 мс | 416 / 175 мс | 51 мс |

(Node, под нагрузкой параллельной генерации миров; в игре те же порядки.)

Как пишется сохранение теперь:
- **Только изменённое.** Сохранение неизменяемо: обновление копирует путь до изменённой записи, остальное
  общее. Текст записей (один отчёт, один полёт, одна цель) запоминается по объекту, и следующий автосейв
  склеивает готовые куски (`src/application/save-json.ts`). Результат побайтно равен `JSON.stringify` —
  это проверяют тест и все Electron-проверки загрузки.
- **Кусками между кадрами.** Автосейв тика считается шагами по 8 мс (`setTimeout` между шагами); команды
  игрока по-прежнему пишутся сразу и целиком. На main весь мир сериализовался каждую секунду.
- **Не чаще раза на 50× стоимости записи** (≤ ~2% UI-потока, не реже раза в 60 с).
- **Большие сохранения — файлом.** Начиная с 8 млн символов текст лежит в `<профиль>/saves`, в
  localStorage — указатель с id записи (`save-storage.ts`, `electron/save-store.cjs`). Файл пишется
  сначала, указатель переставляется после — сбой посередине оставляет прежнее сохранение. Запись
  асинхронная: UI-поток только передаёт текст главному процессу (20 мс вместо 125 мс на 58 млн
  символов), новое значение до конца записи отдаётся из памяти. При закрытии окна (`beforeunload`/
  `pagehide`) недописанное пишется синхронно. Предел localStorage (~52,3 млн) больше не важен.

## Что было медленным и что сделано

1. **Прогон в UI-потоке.** Раньше: задачи по 40 мс, после каждой перерисовка всего App и автосейв мира
   раз в 2 с. Теперь — Web Worker (`src/npc-catchup.worker.ts`, `application/npc-catchup-runner.ts`):
   куски ~250 мс, прогресс через маленький стор (перерисовывается только окно прогресса), прогресс
   сохраняется раз в 15 с с сериализацией в воркере; в конце App берёт только изменённые поля.
   Без воркера или при ошибке — прежний путь.
2. **Досчёт всех владельцев на каждом событии полёта** (почти все 100 NPC с живыми полётами) → только
   владельцы, которых касаются полёты этой точки; полный досчёт в начале среза пропускается, если мир
   уже досчитан на этот момент.
3. **Проходы по тысячам записей на каждое событие.** К дню 2 это ~3 600 полётов: из них ~1 350 зондов
   на орбите и ~2 000 завершённых в суточном архиве; плюс 15–22 тыс. шпионских отчётов. Стало:
   - порядок кандидатов в `reconcileFlights` переиспользуется (на тик было ~70 проходов по всем полётам);
   - отдельный список живых полётов; законность висящих зондов кэшируется;
   - сравнение «до/после» точки — по слотам;
   - индекс отчётов по владельцу продолжается, а не строится заново;
   - ключи отчётов и защита боевых отчётов — через индексы.
4. **Повторные вычисления** → кэши и индексы, каждый привязан к тем частям состояния, которые реально
   читаются:
   - очки владельца (включая стоимость очереди, а не сам массив очереди);
   - отношения владельцев (по структуре союзов);
   - системы для решений NPC (по видимым временным объектам);
   - входы карты и пиратский контакт (не сбрасываются от дохода игрока);
   - отпечаток систем для рейдов;
   - победы над пиратами по системам;
   - выбор пиратских проверок и помощи;
   - текст отказа атаки — только при чтении.
5. **Расписание временных объектов вселенной с 01.01.2026** (~7 000 циклов на систему и вид, ~1 ГБ кучи;
   в UI-потоке и в воркере) → типизированные массивы (~0,1 ГБ вне кучи), построение в простое
   (`requestIdleCallback`), поиск активного цикла останавливается на последнем начавшемся (раньше в
   каждом «тихом» промежутке обходилась вся история — главная статья тика дня 3).
6. **Автосейв каждого тика** → бюджет ~2% (см. выше).
7. **Экран боевых докладов** перечитывал и разбирал всё сохранение каждую секунду → берёт опубликованное
   состояние.

## Детерминизм (красные CI-задачи main)

Причины расхождений и исправления:
- после боя оставались записи командиров с `count: 0` и старым уровнем (загрузка их выбрасывала);
- повторный шпионский отчёт NPC читал ресурсы цели, досчитанные до границы куска → цель досчитывается
  на момент решения;
- журнал разведки рос без предела, а загрузка оставляла 256 → та же граница в рантайме;
- порядок ключей рекордов разведки зависел от нарезки → порядок по id;
- квитанции улучшений космодрома NPC хранились в окне 256, остальные действия — 64 → общее окно 64;
- блокировка перенаселения снималась в момент очередного досчёта → теперь в точный момент сжигания,
  он же контрольная точка прогона;
- окно сводки мира заменялось «неполной» сводкой короткого хвоста прогона (Electron QA полного мира).

Итоговые миры отличаются от main ровно этими исправлениями; правила и поведение NPC те же.
`test:header-ui` падал из-за гонки в самом тесте (ресурсы растут за время перезагрузки) — добавлен допуск
на рост 0,01%.

## Проблемы сохранений

**Исправлено — сохранение «повреждено» из-за последнего бита.** При загрузке профиль пирата
пересоздаётся из сида и сравнивается с сохранённым побайтно. Ожидаемые доли тиров считаются через
`Math.pow/exp`, а последний бит у движков разный: Node 24 даёт 82.27063208603401, Electron 44 —
82.270632086034. Сохранение с профилем, созданным другим движком, открывалось как «Сохранение
повреждено: Повреждены очереди или полёты автономного NPC». Так же сломались бы сохранения всех
игроков при обновлении Electron с другой математикой V8. Теперь доли сравниваются до 12 значащих цифр;
выборка, тир и корабли — по-прежнему точно (`pirates/contact.ts`, тест в `contact.test.ts`).

**Исправлено — мир дня 3 не помещался в localStorage.** Предел Electron 44 — ~52,3 млн символов на
источник; сохранение растёт ~19 млн в сутки и к дню 3 весит 57,7 млн. Запись падала («Не удалось
сохранить игру»), и при следующем запуске грузилось более старое сохранение. Теперь большое сохранение
лежит файлом (см. «Сохранение»). Размер сам по себе остаётся: 40% — 22,6 тыс. шпионских отчётов NPC
(23 МБ), дальше цели (9,8 МБ), полёты (6,8 МБ), журнал пиратских проверок (5,8 МБ) — см. план «максимум».

Проверено на собранной игре с настоящими перезапусками (`npm run test:late-save-ui`, скрытые окна,
одноразовый профиль, каждая фаза — отдельный процесс Electron):
- **миграция:** сохранение дня 2 (39,9 млн символов), лежащее в localStorage как у старой сборки, грузится,
  и первая же запись переносит его в файл (в localStorage остаётся указатель);
- **перезапуск:** этот мир снова грузится после выхода из игры, курсор не откатился;
- **день 3 (57,7 млн, больше предела localStorage):** загрузка, прогон 1 ч в воркере; воркер сохранил
  прогресс (+3,5 игровых минуты), окно закрыто посреди прогона → после перезапуска игра открылась без
  ошибок ровно с сохранённого места и продолжила прогон;
- **закрытие во время асинхронной записи:** главный процесс искусственно пишет файл 4 с; окно закрыто,
  пока запись шла → недописанное значение записано синхронно при закрытии, после перезапуска загружено
  оно, опоздавшая асинхронная запись указатель не перебила.

- **24 ч на мире дня 7 за 1–2 мин — нет.** Профиль прогона 1 ч на дне 3 (HEAD 29.10):
  - 47% — решения NPC (`applyNpcAutonomyAttention`: кандидаты миссий, выбор силы атаки, контекст

  - 13% — полёты;
  - ~10% — досчёт экономик NPC; остальное размазано.

  Это уже не «лишние проходы», а сама работа 100 владельцев, каждый из которых смотрит в игру каждые
  20–40 секунд. Дальше нужны структурные шаги, трогающие модель решений: дешёвый «взгляд» NPC (общий
  контекст на момент, кандидаты по семействам) и инкрементальная очередь полётов по времени события.
  Параллелить нельзя: решения владельцев в одну миллисекунду меняют общее состояние по очереди.
- **Живая игра на дне 3.** После доводки (см. «Живая игра») секунда стоит UI-потоку ~76 мс медианой,
  но одна группа решений NPC — 40–110 мс одним куском: её нельзя разрезать, не меняя модель решений.
  Чтобы убрать это из кадров совсем, мир должен жить в воркере постоянно (пункт 1 плана «максимум»).
- **Замеры на мирах дня 5 и 7** — генерация не закончилась к безопасной остановке; оценка по тренду
  дней 1–3 — в разделе «Прогон отсутствия».
- **CSS-эффекты (blur, backdrop-filter)** не трогал: после правок UI-потока на GPU все экраны держат
  60/120 FPS, CSS не узкое место.

## План следующего шага «максимум»

Решение — делать ли это в этом PR или следующим — за владельцем. Все три пункта не меняют правил игры,
но каждый требует той же проверки паритета побайтными дайджестами, что и этот PR.

### 1. Мир живёт в воркере постоянно

Что: воркер держит авторитетный мир всё время, а не только во время прогона. Живой тик (NPC, полёты,
пираты, обрезка архивов) и сериализация автосейва идут там; UI-поток получает только то, что рисует
(свои планеты, очереди, видимые полёты, уведомления), а команды игрока отправляются в воркер как
сообщения и применяются там в той же точке времени.

Ожидаемый выигрыш по профилю: на дне 3 живая секунда стоит UI-потоку ~76 мс (медиана), пики одной
группы решений NPC 40–110 мс; автосейв — ~70–100 мс вычислений кусками. Всё это уходит из UI-потока:
в простое остаются только рендер и приём изменений, т.е. 60 FPS без длинных задач на днях 3–7
независимо от размера мира. Скорость прогона не растёт (это другая ось).

Риски:
- команды игрока сейчас — сотни колбэков `setState(prev => f(prev))` в App и экранах; их нужно
  перевести на «команда → воркер → результат», иначе мир в UI и в воркере разойдутся;
- передача изменений: структурное клонирование больших полей (цели разведки 10 МБ, отчёты 23 МБ) на
  каждом тике снова съест кадр — нужен дифф по записям (id → запись), а не по полям верхнего уровня;
- экраны, которые читают весь мир (рейтинг, командование, отчёты), должны получать выборки из воркера;
- отказ воркера → нужен прежний путь в UI-потоке как запасной.

Объём: крупный, ~2–3 недели одного разработчика с QA; затрагивает App.tsx, слой application/commands,
все экраны с прямым чтением SaveState. Отдельный PR.

### 2. Дешёвый «взгляд» NPC и инкрементальная очередь полётов

Что:
- общий контекст решения на момент времени (публичная карта, видимые цели, очки, пираты) строится один
  раз на группу событий и переиспользуется всеми владельцами этой миллисекунды, а не собирается каждым;
- кандидаты миссий по семействам (атака/шпионаж/помощь/пираты/добыча) с ранним отсечением: семейство,
  у которого нет допустимых целей, не перебирается;
- очередь полётов как куча по времени следующего события вместо пересборки списка кандидатов при
  изменении записей.

Ожидаемый выигрыш по профилю (день 3, 1 ч прогона, HEAD 29.10, Node 162 с): решения NPC — 47%
времени (`applyNpcAutonomyAttention`: кандидаты миссий 12%, выбор силы атаки 5%, контекст полезности 5%,
пиратские кандидаты 5%, очки владельцев 5%), полёты — 13%. Если «взгляд» подешевеет в 2–3 раза, а полёты
в 2 раза — прогон ×1,5 (1 ч дня 3: 162 → ~105–110 с). В живой игре пики групп решений 40–110 мс → ~20–50 мс.

Риски: это прямо модель решений — любой сдвиг порядка или общей части контекста меняет мир;
нужен побайтный паритет на всех фикстурах и long-horizon. Самый рискованный пункт по детерминизму.

Объём: средний-крупный, ~1–2 недели; npc-autonomy, npc-mission-policy, npc-utility, flights.

### 3. Компактные архивы шпионских отчётов

Что: 22,6 тыс. шпионских отчётов NPC — 23 из 58 млн символов сохранения дня 3. NPC читают из отчёта
только оценку (ресурсы, флот, оборона одной строкой чисел) и время; полный формат нужен только отчётам
игрока. Хранить отчёты NPC в компактном виде (массив чисел, без повторяющихся имён полей), раскрывать
при чтении.

Ожидаемый выигрыш: сохранение дня 3 ~58 → ~38–40 млн символов (−35–40%, оценка по размерам полей),
загрузка и холодный автосейв на столько же быстрее, рост сохранения ~19 → ~12 млн в сутки. Обрезка
архивов сейчас — 20% прогона дня 3 (`pruneCampaignHistory`: скан шпионских отчётов при каждом новом,
сводки полётов, чужие боевые отчёты); с компактными отчётами и инкрементальным индексом «новейший отчёт
на пару владелец–цель» большая часть этого уходит — ещё ~×1,2–1,25 к прогону. Вместе с пунктом 2 —
~×1,8–2 (1 ч дня 3 → ~80–90 с).

Риски: миграция формата сохранений (старые читаются, новые не читаются старой сборкой — нужна версия
схемы); детерминизм не затрагивается, если раскрытие точное.

Объём: малый-средний, ~3–5 дней; espionage, history-retention, persistence + миграция и тесты.

Порядок, если делать всё: 3 (дёшево и снимает давление на хранилище) → 2 (скорость прогона) → 1
(FPS при любом размере мира).

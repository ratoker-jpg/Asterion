# Мигающие Electron QA: причины и исправление (02.11.2026)

Ветка `claude/qa-flaky-saves`. Задача: после PR проверки Electron QA перестают мигать, `main` не краснеет без причины.

## Коротко

- Почти все мигания — одна причина: **QA правит сохранение в работающей игре**, а игра пишет своё состояние поверх (автосейв, сброс отложенной записи при выгрузке страницы, сохранение воркера живого мира). Перезагруженная игра читает старое.
- Сделан единый помощник `electron/qa-save-edit.cjs` (`editSaveIdle`): окно уходит на страницу без игры того же источника (игра при этом сама сбрасывает свою последнюю запись и погибает вместе с таймерами и воркером), правка выполняется там, игра загружается заново и ждёт, пока принимает команды, и проверяется, что она прочитала именно правку. Все скрипты, входящие в CI, переведены на него; самодельные «охранники» записи и циклы «повторить, пока не сохранится» убраны.
- Нашлась и **настоящая ошибка игры** (отдельно, она важнее теста): игра сообщала игроку «команда принята» (уведомление, тост), а новое состояние в React не попадало — запись очереди строительства или обмен просто исчезали. Исправление: `src/application/state.ts` проверяет результат команды против отрисованного состояния и при потере коммитит его явно; `App.tsx` считает такие случаи (`window.__asterionStateHeals`).
- Доказательство — повторные прогоны в GitHub Actions (`.github/workflows/qa-repeat.yml`), цифры ниже.

## Причина 1: QA и игра пишут одно сохранение

Игра владеет сохранением. Пока она работает, его пишут: автосейв после каждого изменения, отложенная запись тиков, `leave`/`onUnload` в `App.tsx` (сброс при `pagehide`/`beforeunload`) и, в боевом режиме, воркер живого мира (текст сохранения приходит сообщением и пишется страницей). QA же делал `localStorage.setItem(...)` или `removeItem(...)` в той же странице и перезагружал её: любой из этих писателей мог успеть после правки. Были и частичные обходы (перехват `Storage.prototype.setItem`, циклы «повторить до трёх раз», `fixture-reload.cjs`), в каждом скрипте свой и с дырами (не закрывали `removeItem`, терялись при записи другого ключа).

Решение — не бороться с писателями, а убрать их: `editSaveIdle` (описание в шапке `electron/qa-save-edit.cjs`). Переведены: command, command-aid, command-journal, reports-profile, repair-workshop, fleet-production, pirate-operations, visual-capture, visual-spaceport-upgrades, visual-trade-center, visual-recycling-center, visual-building-interiors, visual-production-bots, visual-industry-requirements, visual-science, resource-assets, universe-planet, space-flight, simulator, battle-report, test-mode, energy и integration-spaceport-upgrades. `fixture-reload.cjs` удалён. Не переведены скрипты вне CI-шардов (скриншотные `*-screenshots.cjs`, `ui-polish-screenshots.cjs`, `header-qa.cjs`, `cloud-world-qa.cjs`, `catchup-summary-qa.cjs`, `late-*`, `npc-*`, `save-*`): они правят хранилище только до первой загрузки или проверяют само сохранение.

## Причина 2: игра теряет принятую команду (ошибка игры)

Следы (`electron/qa-trace.cjs`: каждый коммит состояния, каждая запись сохранения и каждый клик с цифрой из DOM) из упавших прогонов:

- Обмен: клик по «ОБМЕНЯТЬ» → в компоненте тост «Обмен выполнен · Получено 500 металла», сумма сброшена, уведомление приложения «Обмен выполнен» — но после клика **нет ни одного нового коммита состояния и ни одной записи сохранения**, счётчик слотов остаётся `1/3`.
- Очередь: клик по `data-qa-build-button` для «Ангар» → уведомление «Ангар добавлено в общую очередь» — после клика нет коммита с тремя записями; очередь в интерфейсе и сохранении остаётся из двух.

Команды `build`, `trade`, `recycling`, `bots` и другие идут через `enqueueApplicationStateUpdate` (функциональное обновление + `flushSync`); подтверждение игроку строится по результату функции-обновления, а не по тому, что React отрисовал. Точный механизм потери в React не установлен (воспроизводится только на медленном CI, 3–7 % прогонов `qa:visual`, не локально). Поэтому исправление защитное: после `flush` сравнивается результат команды с состоянием, которое React отрисовал (`renderedStateRef`, присваивается при рендере); если состояния нет, оно коммитится явно, счётчик `window.__asterionStateHeals` растёт, в консоль идёт предупреждение. Модульный тест: `src/application/application.test.ts` («a command result that React never rendered is committed again and reported»).

## Что сделано

- `electron/qa-save-edit.cjs` — помощник; `electron/qa-trace.cjs` — трассировка потерянной команды для QA; `electron/qa-save-edit.cjs#waitForCommands` — ждёт, пока игра принимает команды.
- ~30 скриптов QA переведены на помощник, самодельные охранники и повторы убраны.
- `src/application/state.ts`, `src/App.tsx` — исправление игры (выше), тест в `application.test.ts`.
- `.github/workflows/qa-repeat.yml` — измерение: запускает шарды CI N раз подряд (по раннеру на запуск), считает падения по проверкам и сколько раз сработало исправление игры. Пока файла нет в `main`, запускается пушем в ветку `claude/qa-flaky-*` с `QA-REPEAT ref=<ветка> n=<N> [suite=<npm-скрипт>]` в сообщении коммита; после влития — вручную (`workflow_dispatch`).

## Цифры

Измерение: каждый шард `ci.yml` запускался N раз подряд, каждый запуск на своём раннере GitHub Actions (Windows), 26 проверок × 10 запусков = 260 запусков проверок на прогон.

| состояние кода | запусков | падений | какие |
|---|---|---|---|
| `main` (прогон 41409009168) | 260 | **7** | command-journal 3, command-aid 1, repair 1, reports 1, qa:visual (очередь) 1 — те же тексты, что в истории CI |
| ветка, правки сохранения во всех скриптах, без исправления игры (прогон 41421642168) | 260 | **1** | qa:visual (слот обмена) |
| то же, только `qa:visual` (прогоны 41426875110 и 41428755901) | 70 | **6** | обмен ×3, очередь ×1, слоты ×2 — все «принятая команда не дошла до состояния», со следами |
| + исправление игры (прогон 41431922810, только `qa:visual`) | 40 | **0** | исправление сработало 1 раз (`heals=1`): этот запуск раньше упал бы |
| финальное состояние, все шарды ×10 (прогон 41431986693) | 260 | идёт | смотреть сводку `Failures per suite` прогона |

Итого по «известным мигающим» проверкам: command-ui/aid/journal, reports-ui, repair-ui, pirate-operations-ui, fleet-ui: **было 6 падений из 70 запусков на `main` → 0 из 70 на ветке** (прогон 41421642168; command-ui, command-aid-ui, command-journal-ui, reports-ui, repair-ui, pirate-operations-ui, fleet-ui по 10 запусков). `qa:visual`: было 1 из 10 на `main` и 6 из 70 на ветке без исправления игры → **0 из 40** с ним. Промежуточные прогоны: 41410416693 (3 падения, часть скриптов ещё не переведена) и 41415226600 (qa:visual 10 из 10 — регресс моей промежуточной правки, найден и исправлен: засев `visual-building-interiors` оставался гонкой после сброса).

## Что не доказано

- Механизм потери команды в React не найден: исправление защитное (проверка и повторный коммит), а не устранение причины. Доказательство — следы (нет коммита после «принятой» команды) и падение с 6/70 до 0/40 при одном срабатывании; выборка небольшая. Счётчик `heals` в отчётах прогонов показывает, как часто это происходит; если он останется ненулевым, причину стоит искать в порядке очередей React (`flushSync` + функциональное обновление при ожидающем неблокирующем `setState`).
- Не воспроизведено на `main` (0 из 10): `test:fleet-ui`, `test:pirate-operations-ui`; их причина взята из истории CI и общего механизма, а исправление подтверждено только отсутствием падений на ветке (0 из 10 в прогонах ветки).
- Финальный прогон всех шардов (41431986693) к моменту сдачи отчёта не закончился (очередь раннеров занята другими прогонами); его сводка — в Actions.
- Локально не гонялись тяжёлые наборы (по условию): проверено `npm run build`, `npm run test:inventory`, `test:combat`, `test:reports`, `test:application` (90 тестов, в т.ч. новый), `tsc`, а из Electron-наборов — command, command-aid, command-journal, repair, pirate-operations, fleet, test-mode, energy, visual-capture, visual-trade-center, visual-spaceport-upgrades. `resource-assets-ui` на этой машине падает по геометрии 1920×1080 (и версия из `main` на ней зависает), в CI проходит.

```

```

# Выпуск версий и автообновление

Каждый мерж в `main` выпускает новую версию игры. Установленная игра сама находит её, скачивает в фоне и ставит, когда игрок нажмёт кнопку.

## Номер версии

Версия всегда записывается тремя числами: `MAJOR.MINOR.PATCH`, например `1.4.12`. Буквы в номере не используются: автообновление сравнивает версии по правилам semver, и буквы ломают это сравнение.

| Число | Когда растёт | Как поднять |
|---|---|---|
| **PATCH** (третье) | каждый смерженный PR | ничего делать не нужно, это поведение по умолчанию |
| **MINOR** (второе) | заметное обновление: новая система, крупный экран, большой пересмотр баланса | поставить на PR метку **`release:minor`** |
| **MAJOR** (первое) | глобальная версия: новая кампания, большой перезапуск игры | поставить на PR метку **`release:major`** |

- При `release:minor` растёт MINOR, а PATCH сбрасывается: `1.3.7` → `1.4.0`.
- При `release:major` растёт MAJOR, а MINOR и PATCH сбрасываются: `1.4.2` → `2.0.0`.
- Метку нужно поставить **до мержа**. Метки на PR в CI читаются по коммиту мержа.
- Если на PR обе метки, сработает `release:major`.
- Если два PR смержили почти одновременно и выпуск первого ещё не закончился, следующий релиз учтёт оба PR. Из их меток берётся самая крупная, и номер поднимается один раз.

Стартовая версия — `1.0.0`. Первый релиз после включения автообновления будет `1.0.1`.

## Откуда берётся номер

Номер берётся из последнего тега `vX.Y.Z` на GitHub, а не из `package.json`. В `package.json` всегда остаётся `1.0.0`. CI подставляет номер только в сборку (`-c.extraMetadata.version`) и ничего не коммитит в `main`, поэтому CI не запускает сам себя и не создаёт конфликтов.

Правило вычисления — `tools/next-version.mjs`, тесты — `tools/next-version.test.mjs` (`npm run test:release`).

## Что делает CI (`.github/workflows/ci.yml`)

- **Pull request** — установщик собирается как раньше и лежит в artifact задачи «Windows installer» 14 дней. Релиз не создаётся.
- **Push в `main`** — задача **Release**:
  1. вычисляет следующую версию по тегам и меткам смерженного PR;
  2. собирает установщик с этой версией;
  3. создаёт GitHub Release `vX.Y.Z`. В него входят `Asterion-Setup-X.Y.Z.exe`, `Asterion-Setup-X.Y.Z.exe.blockmap` и `latest.yml`. В заметках — название и ссылка на смерженный PR.
- Задача Release зависит только от собственной сборки установщика. Если упали долгие NPC-проверки, релиз всё равно выйдет.
- Релизы идут строго по одному (`concurrency: release-main`): второй мерж ждёт, пока первый выпустится, и видит его тег. Если вычисленный тег уже занят, берётся следующий свободный номер. Если создать релиз не удалось, задача падает с ошибкой, а не пропускает выпуск молча.
- Право на запись (`contents: write`) есть только у задачи Release.

## Обновление в игре

- Установленная игра проверяет обновления при запуске. Игрок может проверить их и сам: кнопка **«Проверить обновления»** в главном меню (под пунктами меню) и в меню паузы.
- Найденное обновление скачивается в фоне, рядом показываются проценты.
- Без согласия игрока ничего не устанавливается. Когда обновление скачано, появляется кнопка **«Перезапустить и обновить»**. Перед перезапуском игра записывает все сохранения на диск: текущий мир, время игры и большое файловое сохранение. Если в этот момент идёт прогон отсутствия, сохраняется его последний записанный шаг. После обновления прогон продолжится с этого места.
- Сохранения лежат в профиле пользователя (`%APPDATA%\asterion`), а не в папке установки, поэтому обновление их не трогает. `appId` (`com.asterion.game`) и имя пакета (`asterion`) менять нельзя, иначе игра будет искать сохранения в другом месте.
- Если сети нет или GitHub недоступен, в меню появится строка «Нет связи с сервером обновлений · попробуйте позже». Окон с ошибками нет.
- В dev-режиме (`npm run desktop`) и в QA-скриптах обновления не проверяются. В установленной игре их можно отключить переменной `ASTERION_DISABLE_UPDATES=1`.

## Облачный сервер

Каждый релиз публикует ещё и `asterion-server-X.Y.Z.tgz` — серверный бандл из того же кода
(`npm run package:server`). Сервер раз в 30 минут (и сразу, когда игра новой версии выгружает
мир) ставит бандл последнего релиза рядом с прежними и перезапускается; живой мир переезжает в
новый релиз с контрольной точки и живёт дальше — прогресс сервера обновление не сбрасывает, а игра
новой версии забирает мир без «другой версии». Подробно — `server/deploy/README.md` и
`docs/reports/SERVER_CATCHUP_2026-10-31.md`.

## Подпись и SmartScreen

Установщик не подписан сертификатом. Поэтому при **первой** установке Windows SmartScreen может показать «Windows защитила ваш компьютер». Чтобы продолжить, нажмите «Подробнее» → «Выполнить в любом случае». Обновления ставятся без этого окна.

Проверка подписи обновлений (`publisherName`) намеренно не включена: без сертификата неподписанные обновления просто не установились бы.

## Как выпустить версию

- **Обычный PR** — просто смержить. Выйдет `X.Y.(Z+1)`.
- **Minor** — поставить метку `release:minor` на PR до мержа, затем смержить.
- **Major** — поставить метку `release:major` на PR до мержа, затем смержить.

Если метки ещё нет в репозитории, её можно создать один раз: GitHub → Issues → Labels → New label, либо `gh label create release:minor` / `gh label create release:major`.

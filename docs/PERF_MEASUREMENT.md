# Мерило 120 FPS

Цель владельца: фиксированные 120 кадров в секунду на мониторе 120 Гц, без потери качества и без потери детерминизма. Аудит: `PERF-AUDIT-2026-11-10.md` (лежит у владельца, не в репозитории). Этот файл - как мерить до и после в каждом PR программы (PR 2-9).

**Правило:** замер идёт только на GitHub Actions. На компьютере владельца ничего из этого не запускается.

## Что есть

| Что | Где | Зачем |
|---|---|---|
| Счётчик кадров в игре | Настройки → Экран → «Счётчик кадров»; код `src/ui/frame-meter*.ts` | Владелец видит просадки глазами: кадры/с, худший кадр за 5 с, кадры > 8,3 и > 16,7 мс, долгие задачи. Выключен - не считает ничего |
| Кадры по экранам на тяжёлом мире | `.github/workflows/perf-audit.yml`, `electron/perf-audit-trace.cjs` | Трассировка Chromium на 120 Гц по 9 экранам и окну автосейва |
| Таблица и порог | `tools/perf-audit-summary.mjs` | Превращает JSON в таблицу в сводке запуска и проверяет порог |
| Живой мир по тикам | `tools/perf-audit-live.mjs` | Воркер, патч по секциям, цена сохранения, равенство зеркала |
| Старый замер переключения экранов | `electron/late-game-fps-qa.cjs` (`npm run test:late-game-fps-ui`) | Теперь 120 кадров/с вместо 60; в CI пропущен |

## Как запустить замер

```bash
gh workflow run perf-audit.yml -R ratoker-jpg/Asterion --ref <ветка PR>
```

Мир: день 3, 100 ботов, максимальная активность (как `activity_cpu` в bot-lab). Он генерируется один раз и лежит в кэше `perf-fixture-100-max-v1`, поэтому все PR сравниваются на одном и том же мире. Если старый мир перестал читаться после смены формата сохранения, поднять `FIXTURE_CACHE_VERSION` в workflow. Можно взять мир из чужого запуска: `-f fixtures_run=<id>` (артефакт `activity-fixture-100-max`, хранится 3-7 дней).

Параметры трассировки: `--motion` включает анимации (Windows-раннер сообщает «уменьшить движение», игра их выключает), `--no-raf` убирает собственный цикл кадров (он сам заставлял бы поток интерфейса рисовать каждый кадр), частота кадров 120. Один экран - 5 секунд; окно автосейва - 90 секунд на экране планеты.

## Что в таблице

Для каждого экрана: долгих задач в секунду (>50 мс), задач длиннее кадра 120 Гц (8,3 мс) и длиннее 16,7 мс за окно, худшая задача, сбросы кадра в секунду (`DroppedFrame`), коммитов React в секунду, больших сборок мусора, куча окна. Под таблицей: худшая задача окна автосейва и нарушения порога. Полный JSON - артефакт `perf-frames-100-max`.

Задача потока интерфейса длиннее 8,3 мс - это пропущенный кадр: поэтому «задач > 8,3 мс» и есть счёт пропущенных кадров по трассировке. На Actions нет видеокарты, поэтому отрисовке и растру из этих цифр верить нельзя; цифрам JavaScript, стилей, раскладки и сборки мусора - можно.

## Порог

Задан константами `GATE` в `tools/perf-audit-summary.mjs`. Сейчас он **только отчёт**: значения широкие, `ENFORCE_BY_DEFAULT = false`, CI не падает. Конечная цель аудита: худшая задача меньше 8 мс и ноль задач длиннее 8,3 мс. Каждый PR, который доказал выигрыш, сужает константы и, когда цель достигнута, включает проверку (`--enforce` или `ENFORCE_BY_DEFAULT = true`).

## Как PR отчитывается «до и после»

1. «До»: запуск `perf-audit.yml` на `main` (или на базовом коммите PR). Номер запуска записать в описание.
2. «После»: тот же запуск на ветке PR, **с тем же миром** (кэш даёт его сам; при ручном мире - тот же `fixtures_run`).
3. В описание PR вставить две таблицы из сводок запусков и одну строку: какие колонки улучшились. PR на скорость без цифр не принимается.
4. Если PR трогает воркер, добавить `tools/perf-audit-live.mjs` (`perTick.tick`, `perTick.patchKb`, `equal` обязан быть `true`).
5. Шум раннера есть: если разница в пределах нескольких процентов, перезапустить и взять худший из двух.

Сам PR 1 ничего не ускоряет: его цифры - исходная точка для PR 2-9.

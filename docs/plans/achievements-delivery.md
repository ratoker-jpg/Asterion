# Достижения Asterion — план реализации

Пользователь утвердил итоговый экран из PR #239. Список из варианта A показывает условия и прогресс в строках. Шапка из B показывает медаль, очки и путь к следующему рангу. Справа открываются подробности выбранного достижения. Эталон — `docs/design/identity/mockups/achievements-a.html?hero=1` и кадры `docs/design/identity/shots/{1280x720,2560x1080}/ach-final.jpg`.

База — `origin/main` на `f35b04ab`. В `src/ReportsView.tsx` уже есть вход «Сообщения → Достижения». `src/domain/rating/scoring.ts` пока возвращает `achievementPoints: 0`. Условия и очки берём из `docs/design/identity/catalog.js` и `docs/design/IDENTITY-AND-ACHIEVEMENTS.md`. Условия, которые нельзя вывести из текущих данных, сверяем с концепцией до подключения конкретного достижения.

## PR 1. Игровой экран и первые достижения

В ветке `codex/achievements-screen` заменить пустую вкладку. Подключить несколько достижений развития, условия которых подтверждаются текущим состоянием игры. Это первый сквозной сценарий для каталога, начисления, летописи и экрана. Сделать фильтры раздела и статуса, выбор записи, подробности, ранги и экраны для пустого результата и максимального ранга. В шапке использовать реальные очки, ранг и прогресс. Карточки магазина и действия с титулом появятся в соответствующих PR.

Первый набор — `builder`, `architect`, `empire-architect`, `colonist` и `power-grid`. Вместе они дают 110 очков, поэтому игрок может получить первый новый ранг за 100 очков. Новая игра уже содержит здания первого уровня, поэтому `first-stone` подключается, когда появится надёжный сигнал о завершённой игроком постройке. Летопись первого PR хранится локально на компьютере. Облачный слот переносит состояние кампании, по которому можно зачесть подтверждаемые вехи, а отдельная история начислений между компьютерами не синхронизируется.

Согласовать контракт между расчётом достижений и экраном до параллельной работы над ними. Для летописи сверить хранилище серии (`electron/persona-file.cjs`, `src/application/persona-store.ts`, `src/application/npc-series.ts`) и путь облачных сохранений. Повторная загрузка, копия слота или повтор обработки события должны возвращать тот же результат. Для постоянной вехи зачёт единожды, для подвига раунда — единожды в пределах стабильного идентификатора раунда. Тестовый режим держит отдельный прогресс.

Приёмка. Выполнить условие через обычный игровой экран и увидеть изменение прогресса, получение и начисление очков. Открыть старый сейв с уже выполненным проверяемым условием и подтвердить зачёт. Перезапуск, копия слота и повтор обработки не начисляют очки снова. На 1280×720 и 2560×1080 сверить список, шапку и правую панель с эталоном, проверить крайние состояния и работу фильтров с клавиатуры.

Команды для повторной проверки — `npm run test:reports`, `npm run test:inventory`, `npm run build`, `npx electron electron/achievements-qa.cjs` и `npm run test:messages-screens-ui`. В Electron проверены уровни 14, 15 и 25 на обоих целевых размерах. Отдельный сценарий запускает стройку уровня 15 кнопкой в игре, переносит срок готовности записи очереди в тестовом сохранении и подтверждает завершение через игровой код и начисление 10 очков.

## PR 2. Полная летопись, письма и рейтинг

После PR 1 подключить 71 позицию каталога Opus. Группы источников — развитие, флот и бой, разведка, космос и пираты, союз, Солнце и Врата, подвиги раунда и летопись. Где это возможно, выводить прошлые достижения из сохранения и серии. Боевые, раундовые и прочие событийные условия обновлять на соответствующих игровых событиях. Подключить уведомления о получении и реальные заработанные очки к данным рейтинга и профиля. Сверить поведение для игрока и NPC с концепцией.

Приёмка. У каждой позиции каталога есть проверяемый источник прогресса. Один и тот же подвиг даёт очки снова в другом раунде. Постоянная веха сохраняется между раундами. Уведомление о выдаче приходит один раз. В рейтинге и профиле показывается одна и та же сумма.

## PR 3. Титулы и витрина профиля

На базе PR 2 подключить «Сделать титулом» и «Показать в профиле». Игрок выбирает уже полученное достижение. Использовать существующие данные игрока и профиля для отображения выбранного титула на предусмотренных концепцией поверхностях.

Приёмка. Полученное достижение можно выбрать и заменить. Выбор переживает перезапуск. Недоступное достижение выбрать нельзя. Профиль, рейтинг и другие подключённые места показывают один и тот же титул.

## PR 4. Облики за очки

На базе PR 2 и уже влитого каталога обликов планет из PR #240 подключить к шапке превью наград и остаток очков. Добавить «Облик» с разделами «Надето» и «Магазин». Применить правила покупки и разблокировки из концепции. PR 3 и PR 4 можно готовить параллельно, с заранее закреплённым владельцем общего экрана и последовательной интеграцией изменений в него.

Приёмка. Покупка при достаточном балансе списывает очки один раз и переживает перезапуск. Заработанная за всё время сумма в рейтинге сохраняется после покупки. Облики за достижения и победы открываются по соответствующим условиям. При нехватке очков состояние покупки и баланса сохраняется.

## Координация и выпуск

- GPT‑6.2 Sol с уровнем рассуждений `medium` отвечает за визуальный эталон, состояния экрана и проверку кадров. Демонстрационные цены, баланс, даты, редкость и титулы из HTML берутся в игру только из соответствующих данных.
- GPT‑6 Luna с уровнем рассуждений `xhigh` отвечает за реализацию. Работа над первым игровым сценарием запущена в `codex/achievements-screen`.
- Координатор утверждает контракт между механикой и экраном, разводит меняемые файлы между исполнителями, собирает ветки и ведёт проверки. Каждый игровой PR проходит целевые тесты, доменную прогонку, сборку, Electron QA и Windows-упаковку. PR остаются черновиками до решения владельца.
